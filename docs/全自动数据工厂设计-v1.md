## 零、一句话概述

给它一份"待采源清单"，它自己按窗口开工、自己断点续采、自己清洗校验、自己按州发布到 Releases、自己通知我们；
运行器被回收、网络抖动、源站改字段，都不会让整批任务烂尾。

## 一、两条铁律（不可协商）

### 1.1 数据铁律 —— 绝不编造

1. **只收录真实存在的门牌点地址**；没有门牌号的记录一律丢弃，不猜、不补、不生成。
2. 区间型数据只取每侧两端，不插值、不铺满。
3. 每条记录必须能溯源：保留 `sources`（来源源标识）与 `source`（本批主源）。
4. 不做任何"看起来像地址"的合成数据。宁可少，不许假。

### 1.2 采集铁律 —— 绝不给公共服务添负担

1. **分页取服务端上限的 90%**（`safe_page_size`，见 `collectors/politeness.py`），不试探上限。
2. **单主机最小请求间隔 ≥ 0.8 秒**，由 `Politeness` 全局限速器强制执行。
3. 每主机并发 ≤ 3；跨主机才允许并行。
4. 遇 429 / 403 立即退避并冷却该主机，不重试硬撞。

## 四、关键设计决策（逐条）

### 4.1 接续采集（已实现，保留）

- 单段自带硬上限 `--max-seconds 960`，**到点自己 exit 0**，不 passive 等 GitHub 回收。
- 停之前把断点写入 `progress.json`（`{source_id: {last_oid, done, fetched, ...}}`）。
- 下一段读断点，从 `last_oid + 1` 继续；**泳道声明下限做钳制**（`lo = max(lo, LANE_LO)`，否则泳道 B 会从 1 重采、白干一半 —— 已修）。
- 被回收时的最坏损失 = 一个段（≤16 分钟），且状态未推进 → 下一段重做该段，不丢数据。

### 4.2 打包式分派（**新增，收益最大**）

现状浪费：每个 16 分钟段只处理 1 个源，而 **88% 的源规模 < 20 万条**（777 个源 < 5 万条），
小源在 0.8 秒/请求下 45 秒就能采完 → 槽位利用率约 5%。

改法：一个段领一个**源队列**，循环采集直到时间预算用尽：

```
for src in queue:
    if 剩余预算 < 60s: break
    fetch(src)          # 逐源采集
    write_state(src)    # 逐源写状态 → 段末统一提交
```

预期：槽位利用率 → ~95%，**等效算力提升近 20 倍**。

### 4.3 按"桶"调度（**新增，决定天花板**）

"一个主机"的定义直接决定吞吐：

| 桶定义 | 每日有效吞吐 | 全美耗时 |
|---|---|---|
| `*.arcgis.com` 视为一个桶 | 1.25 req/s | ~19 小时 |
| 按 hostname 分桶（services1…servicesN） | ~11 req/s | ~2~3 小时 |
| 按 hostname + org 路径段分桶 | 更高 | 更快 |

**源表实测**：`services1.arcgis.com` 103 源、`services3` 97、`services.arcgis.com` 95、`services2` 82、`services6` 50，
**最忙 20 个主机承载 700 个源（55%）**；全局仅 **565 个不同主机**。

**结论**：桶 = `hostname`（`*.arcgis.com` 再按 org 路径段细分），
并对 `*.arcgis.com` 家族设**总量闸**（如合计 ≤ 6 req/s），遇 429 自动退避冷却该桶。
同一桶内**同一时刻只允许一条泳道**，保证 ≥0.8s/请求。

### 4.4 进度状态存哪里

- 状态是**小 JSON**（每个源几十字节），**提交进仓库**（如 `state` 分支或 `data/state.json`），不违反"数据集不入库"。
- 理由是必需的：① 让管线知道走到哪，重跑不重复；② 仓库每日有活动 → 避免 GitHub「60 天无活动自动禁用定时任务」。
- **状态只在数据 artifact 上传成功后推进**，避免"状态说完成、数据没上传"的静默丢数据。

### 4.5 发布结构：按州一个 Release，永久复用

```
Release  data-us-ca        ← 每州一个固定 tag，永久复用（全美 51 个，全球按国家/州展开）
   ├─ us-ca-addresses.ndjson.gz              稳定视图（下游只认它，URL 永不变）
   ├─ us-ca-addresses.manifest.json          行数 / sha256 / 来源 / 规则版本 / 抽检结论
   ├─ us-ca-full-2026-10-11.ndjson.gz        当日全量快照（回滚点 + 下批合入基准，留 10 份）
   └─ us-ca-batch-2026-10-11.ndjson.gz       当日新增原始（重建用，极小，留 30 份）
```

**硬约束（GitHub 机制）**

- **tag 不可重复创建** → 绝不能"每次更新加新 tag"（那才会变成 N 个加州）。
- 增量更新 = **删旧资产 + 同名重传**（`gh release upload --clobber`）。
- **单资产上限 2 GB** → 按州分片天然安全（全美合计约 **1.2 GB**，按州最大加州约 **130 MB**）。
- **Release 资产不会过期**（Actions artifacts 才会 30/90 天过期 → **artifacts 不能当持久存储**）。
- 覆盖后稳定 URL 不变；但**资产内部 ID 会变** → 下游不得缓存直链。
- 仓库设置**不要开 "immutable releases"**，否则无法原地更新。

### 4.6 三层数据与"覆盖"的安全语义（**最关键**）

**GitHub 的覆盖是纯整体替换，不做任何合并/追加。** 因此：

| 层 | 文件 | 语义 | 保留 |
|---|---|---|---|
| 稳定视图 | `us-ca-addresses.ndjson.gz` | 下游读取的当前全量 | 永远 1 份（可覆盖） |
| 全量快照 | `us-ca-full-<date>.ndjson.gz` | 回滚点 + 下批合入基准 | **10 份** |
| 批次原始 | `us-ca-batch-<date>.ndjson.gz` | 全量重建的原材料 | **30 份** |

**绝不能用"增量包"做覆盖** —— 会当场抹掉历史数据。
**增量的是采集过程，不是发布物**：发布物永远是"全量快照"。

**每日动作顺序（顺序不可调换）**

1. 下载昨日 `full` 作为合入基准
2. 并入本窗口新采数据 → 按主键去重 → 生成今日 `full` 与 `batch`
3. 先上传 **`full`（新文件名）+ `batch`（新文件名）** —— 新名字，绝不覆盖任何东西
4. **下载回来复核**：行数、sha256 是否与 manifest 一致
5. 复核通过 → 最后才 `--clobber` 覆盖稳定视图
6. 复核不通过 → **什么都不覆盖**（稳定视图仍是昨天版 = 自动回滚）
7. 清理超过保留份数的旧文件 → 通知

> 清理必须放在**最后一步**：先删后传 = 一旦传失败又无旧版兜底 = 净损失。

### 4.7 校验闸门与抽检（真校验，非自证）

**A. 规则校验（100% 全量过）**

| 项 | 规则 |
|---|---|
| 州/地区码 | 必须命中白名单（50 州 + DC/PR/VI/GU/AS/MP；全球扩展为各国一级行政区表） |
| 门牌号 | 必须匹配 `^\d{1,6}[A-Z]?$`（或各国等价规则） |
| 门牌号 ≠ 邮编 | 命中即丢弃（整串地址兜底残留的典型特征） |
| 街道 | 非空；不得以邮编开头；不得包含城市名/州名残片 |
| 主键唯一 | 去重后库内无重复键 |
| 行数一致性 | 稳定视图行数 == manifest 行数 |

**B. 抽样回源比对（关键步骤，机器可做）**

随机抽 **200 条**，带 `OID` 回源查询（ArcGIS 支持 `where=OBJECTID=n`），逐条比对
门牌号 / 街道 / 城市 / 邮编是否与源一致。

- 这是**唯一能证明"数据没编造、没串行错位"**的手段；纯内部规则自检查不出映射错误。
- 通过阈值建议：**一致率 ≥ 99.5%**，否则本批不发布。
- 报告随 release 一起上传（`verify_report.json`）。

**C. 熔断**

抽检失败率超阈值、或连续 3 个窗口运行器回收率异常 → **本窗口内停止派发**，等下个窗口。

### 4.8 通知链路

- **主路**：workflow 调 Telegram Bot `sendMessage`（token 放 Secrets），消息含：州、条数、行数、sha256 前 8 位、校验结论、release 链接。
- **兜底**：本机 cron 每 5 分钟轮询 Releases API（零配置、零暴露、不依赖外部凭据）。
- **双路都留**：主路即时，兜底防漏。

### 4.9 运行时间表（每天 10 小时，双窗口）

#### 各区域源站的高峰 / 低谷（北京时间）

| 区域 | 源站高峰（避开） | 源站低谷（该打） |
|---|---|---|
| 美国 | 21:00–06:00 | **07:00–20:00** |
| 欧洲 / 非洲 | 14:00–24:00 | **00:00–14:00** |
| 日韩台 | 08:00–17:00 | 00:00–07:00 |
| 澳新 | 07:00–15:00 | 15:00–07:00 |
| 印度 | 11:30–20:30 | 20:30–11:30 |
| 拉美 / 巴西 | 20:00–05:00 | 05:00–19:00 |
| **全球国际骨干** | **19:00–24:00** | 其余时段 |

#### 时间表（严格满足四条约束：03:00 起 / 双窗口 / 窗口间停 1~5 h / 每日实跑 10 h）

**窗口 A（固定，03:00 开始，窗口内含 1 小时呼吸）**

| 时段（北京） | 动作 | 实跑 |
|---|---|---|
| 03:00 – 05:00 | 跑（亚太 / 南半球低谷） | 2 h |
| 05:00 – 06:00 | **停 1 小时**（呼吸） | 0 |
| 06:00 – 08:00 | 跑 | 2 h |

窗口 A 实跑 **4 小时**；对齐亚太低谷（日韩台 04:00–08:00 深夜、澳新凌晨、印度后半夜）。

**窗口 B（6 小时，按当日主攻区域二选一，与 A 之间间隔 1~5 小时）**

| 当日主攻 | 窗口 B 时段 | 与 A 的间隔 | 对齐区域 |
|---|---|---|---|
| **美加 / 拉美** | **12:00 – 18:00** | 停 **4 h**（08:00–12:00） | 美东 00:00–06:00、美西 21:00–03:00 —— 美国源头全天最深谷 |
| **欧洲 / 中东非** | **09:00 – 15:00** | 停 **1 h**（08:00–09:00） | CET 03:00–09:00 —— 欧洲上班前的深谷 |

- **每日实跑 = 4 h（A）+ 6 h（B）= 10 小时**，其余时间全停。
- **19:00 – 次日 03:00 完全不跑**（全球国际骨干最挤时段，美欧同时在线）。
- 窗口 B 按 **2 天一轮换**（奇数日美加、偶数日欧非）：48 小时内两片区域各吃到一次深谷，而每天仍然只跑 10 小时。
- 若某天只打一片区域（例如美加冲刺），窗口 B 固定 12:00–18:00，把切换成本全给美加。

#### 窗口内的三个硬要求

1. **波浪式启动**：16 条泳道每 3 分钟起一条，不要同一秒全开（避免开闸式脉冲）。
2. **到点必停**：调度器派发前检查"距窗口结束是否 ≥20 分钟"，不足则不派新任务。
3. **窗口最后 30 分钟**留给 merge → verify → publish → cleanup → notify。

### 4.10 并发与配额

- 免费公仓并发上限 **20 job** → 分配：**16 条采集泳道 + 4 条**（merge / verify / publish / notify）。
- 公仓 Actions 分钟数不限，但**主动自限**：每日 10 小时窗口即上限，不做 24 小时连跑，
  并把每日派发量与并发写成常量，一眼可审计。
- `CHUNK`、泳道数、段预算、窗口时段、保留份数全部做成 workflow input，可随时调。

## 五、数据模型

### 5.1 记录（`*.ndjson` 一行一条，UTF-8，不转义非 ASCII）

```json
{"state":"OH","city":"DAYTON","zip":"45433","street":"MIDDY DR","number":"1016",
 "key":"OH|DAYTON|45433|MIDDY DR|1016","sources":["us/oh/statewide"]}
```

| 字段 | 说明 |
|---|---|
| `state` | 一级行政区码（美为 2 位州码；全球扩展为 ISO 3166-2 细分码） |
| `city` / `zip` / `street` / `number` | 已归一化（大写、去标点、路型缩写 USPS 化） |
| `key` | 去重主键：`state\|city\|zip\|street\|number` |
| `sources` | 来源源标识数组（可追溯，禁删） |

### 5.2 manifest（`*.manifest.json`）

```json
{"region":"us-ca","generated_at":"2026-10-11T03:20:00Z",
 "rows":15000000,"sha256":"...","files":{"view":"us-ca-addresses.ndjson.gz"},
 "sources_count":173,"normalize_version":"1.0.0","key_definition":"state|city|zip|street|number",
 "verify":{"mode":"sample_200","match_rate":1.0,"passed":true},
 "retention":{"full_keep":10,"batch_keep":30}}
```

**`normalize_version` 与 `key_definition` 必须落盘** —— 一旦清洗规则或主键定义变更，
**禁止在旧快照上增量合并**（旧数据是老规则产物，硬并会得到自相矛盾的混合体），
必须**用 `batch` 原始包全量重建**。

## 六、容量与成本估算（全球量级）

- 全球门牌点总量：**5 ~ 10 亿条**量级
- 改造后有效吞吐：约 **2.6 亿条/天**
  （算式：16 泳道 × 1,125 条/秒 × 40% 有效利用率 × 36,000 秒 = 2.59 亿条）
- **全球首轮理论耗时 1.9 ~ 3.9 天**；计入运行器回收浪费、合并排序、发布开销 → **现实预期 3 ~ 5 天工厂时间**
- 存储：压缩后约 **8.5 字节/条** → 10 亿条 ≈ **8.5 GB**（分州后单资产远低于 2 GB 上限）
- 现金成本：**0**（公仓 Actions 不限分钟；Releases 资产不计费）

**真正的瓶颈不是机器时间，而是各国的字段映射与清洗规则**（人工判断），
所以策略是：机器窗口永远有活干（先跑美加），同时并行准备下一国的规则，避免空转。

## 七、分阶段实施

## 八、风险与边界（必须知情）

| 风险 | 说明 | 缓解 |
|---|---|---|
| 平台规则灰区 | 公仓 Actions 免费，但把 runner 当长期数据农场属于灰区 | 自限：每日 10 小时、固定并发、不做 24 小时连跑 |
| 定时器被禁用 | GitHub 仓库 60 天无活动会自动禁用 scheduled workflow | 每日提交状态 + 每日心跳任务 |
| 运行器回收 | 20~50 分钟随机回收 | 16 分钟自停 + 断点续采（已验证） |
| 源站改字段 | 映射过期会"整源 0 条"或产出脏数据 | `mapping_sanity` 预检 + 州码白名单 + 抽样回源 |
| 错误沿链条传播 | 增量累积型管线的通病 | `batch` 原始包可全量重建；`normalize_version` 变更即重建 |
| 覆盖窗口 | 删旧→传新之间有短暂缺失 | 先传版本化资产 → 复核 → 最后覆盖（窗口压到几秒） |
| 令牌/密钥 | PAT、TG token | 只放 GitHub Secrets，明文不进仓库、不进日志 |
