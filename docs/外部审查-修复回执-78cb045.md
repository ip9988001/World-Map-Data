## 修复过程中新发现（本轮回执自查）

**发布不可复现：同一批输入两次构建，分片 sha256 不一致**
- 根因：`sort` 默认**不保证稳定**，同一个 key 下多条记录的相对顺序会变 →
  合并时「取第一条非空值」跟着变（实测差在 `city_src` 标记的有无上）。
- 触发条件：同 key 跨源合并（正是第 11 步要做的事）→ 只要发生合并就可能不可复现。
- 改法：`sort -s`（stable）+ 输入文件列表也排序 → 输入顺序完全确定。
- 实测：连跑 3 次，AK/CA 两个分片 sha256 完全一致。
- 这条也正好回答了原报告清单 A5 里「`sort` 的 locale 与稳定性」那个问句：**稳定性确实是个真问题**，
  而且它不是理论风险 —— 它在第一轮修复里就真出现了。

**同址双 key（原报告未提交）**
- key 用「原始 city/zip」拼成，而字典补齐发生在分组之后 → 同一条街同一个门牌会有两个 key，
  补完 city 后两条五要素都齐、都判 A → **site/ 里同址两条记录**，而唯一 key / 跨州重复都看不见。
- 改法：入全局表**之前**就用字典补 city/zip 并重算 key（`canon_key`），两条会合并成一条（sources 并集）。
- 连带影响：溯源检查（`provenance_check`）也必须用同一把尺子重算 key，否则会误报「发布丢数据」——已同步修。
