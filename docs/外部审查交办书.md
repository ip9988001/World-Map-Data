## 1. 这个项目要做什么（一句话）

公开采集**美国真实地址（门牌点）**，建立可溯源的数据集，服务后续的「美国地址生成器」网站
（对标 meiguodizhi.com，**取用型工具站**：点一下给一条真实存在的地址，**不是检索/查询站**）。

**硬底线**：对外提供的地址必须真实存在，**且每条都能溯源**（官方机构 + 原始接口 URL + 许可 + 采集时间 + 加工过程）。
不能自称权威，但必须做到"如实、可点、可复核"。

**不需要讨论的事**：安全加固、凭据管理、风险提示。资产归委托人本人所有，评审请把精力放在
**数据正确性、流程自洽性、可复核性、成本与可维护性**上。

## 2. 已拍板的铁律（审查时以它们为"不可放宽"的基准）

1. **LLM 只出现在第 3 步（造规则）**，产出物是数据（声明式 spec / 契约）；运行期全是纯 Python，可复现、可回滚。
   反例（要检查有没有出现）：让 LLM 在流水线里逐条判断"这条地址对不对"。
2. **前置门（第 1~4 步）判「采不采」，后置门（第 13 步）判「发不发」，两套不许混用。**
   误杀可以由复检救回；漏放不可逆 → 前置门宁可拒。
3. **永远不允许"降级到能通过"**：源级契约只能声明**豁免/降级**，
   阈值只能**比全局更严**（`min(全局, 声明值)`），豁免必须留痕、可撤销。
   被豁免的源交付**照样降级、永不当 A 级**。
4. **采集值与推断值必须分开记**：补出来的字段一律带 `*_src`（`derived` / `scope_default` / `zip_map`），
   直接采到的字段不带标记（缺省即 source）。
5. **不许静默 0 行 / 不许写前计数**：下载空档、格式缺口、0 产出都必须显式标缺陷或失败，
   清单里的行数/sha256 **必须由"写完回读"得到**。
6. **交付 schema 是白名单**：内部字段（`_rule` 等）一律不出厂。
7. **每条记录必须可溯源**：`sources` 非空、孤儿来源率 0、license 缺失显式标 `unknown`（不许假装有）。

## 4. 重点审查清单（按优先级）

### A. 能不能骗过闸门（最想让你挑的）
1. `collectors/local_cascade.py::_record_ok` 要求"门牌号必须在原始行里真实出现过"（反造数）。
   这个判据能被什么样的数据骗过？举出具体反例。
2. `_gate` 四道门（反造数 / 覆盖率 / 字段完整性 / 脏值率）：
   有没有"能通过四道门但仍是垃圾"的形态？四个阈值里哪个最容易被上游形态"迎合"？
3. `scripts/build_release.py` 的分级：A 级只要求五要素非空。
   有没有"五要素齐但明显不是一个真实可投递地址"的形态？（想想：号与街不匹配、街名是拼接残渣、城市与 ZIP 不属于同一州）
4. `scripts/verify_release.py` 的出厂硬门（空行率 0 / 行数==唯一 key / 孤儿来源 0 / sha256 对账 / 逐州缩水 ≤10%）：
   哪一道是**看起来严格但没有实际防护力**的？漏了什么检查？
5. 溯源链：`sources.json` + `sources-<ST>.json` + 源总表。读者拿到一条记录，
   能不能真的独立复核到上游原始接口？链条上哪一环是断的或不可验证的？

### B. 流程自洽性
6. 第 11 步"全局按 key 排序 + 按 key 的州分片"（`build_release.py::build_global_tsv` / `write_shards`）：
   有没有漏掉的边界（key 异常、跨州、ZZ 兜底桶、内存/file handle 上限、`sort` 的 locale 与稳定性）？
   注意：分片内唯一 key 是用"相邻 key 变化"流式统计的，依赖分片按 key 有序 —— 这个前提在哪些情况下会破？
7. 同 key 多来源合并的字段冲突消解是"优先级新者优先 × 非空优先"。
   在什么情况下这会产出**自相矛盾**的记录（如县名与 county_fips 对不上）？还有别的同类风险吗？
8. 第 3 步声明的质量契约（`rule_author.py::emit_contract`）→ 第 9 步闸门（`local_cascade.load_contracts`）：
   这条桥有没有可能被上游（LLM 输出）或历史文件状态污染（旧行残留、同源重复行、编码问题）？
9. `state.json` 的状态合并（assemble 作业里"同源取 updated 最新者"+ 防缩水护栏）：
   有没有会丢状态/把状态写坏的路径？

### C. 成本与可维护性
10. 全量发布现在是"每次重建全部州分片 + 全量单文件快照"。
    随着数据增长，哪一步会先炸（时间 / 磁盘 / GitHub Release 限制 / 内存）？给出可量化的估计与最小改法。
11. 哪些地方是"看起来通用但其实只对当前几个源成立"的隐含假设？
12. 有没有"改一处不会改另一处"的残留分叉？（按设计文档，原本有 4 处，已归档 5 份文件，核对是否清干净）

### D. 产品契合度（次要但有价值）
13. 目标是"取用型地址生成器"。以当前交付结构（按州分片 + A 级站用子集 + 溯源表 + 字典层），
    能不能直接支撑"点一下给一条"，且每条都能显示"来源机构 + 原始链接 + 采集日期"？
    缺什么？如果让你设计从分片到页面首屏静态 HTML 的最小路径，会怎么做？
14. 面向 AI 引擎的可引用性（GEO）：每条地址带"机构 + 链接 + 采集日期 + 许可"是优势。
    当前打包方式有没有阻碍这一点的地方？

## 6. 请这样给结论（否则不好落地）

1. **每条结论必须带证据**：`文件:行号` + **最小复现路径**（能构造的输入）+ 你期望的行为 vs 实际行为。
   没有证据的判断请标注「推测」。
2. **按严重度分级**：
   - **P0**：会产出"看起来合格但是假/错"的数据，或会静默丢数据 —— 必须在开跑前修
   - **P1**：会造成误杀好源、成本失控、状态损坏 —— 建议开跑前修
   - **P2**：可维护性 / 设计一致性 / 产品契合 —— 可以边跑边修
3. **每条给出最小改法**（改哪个函数、加什么断言），不要只说"建议重构"。
4. 明确列出**你没能验证的部分**（缺什么材料、缺什么环境）。
5. 如果你认为某条铁律（第 2 节）本身是错的，请单独成节说明理由与替代方案 ——
   铁律可以挑战，但要给出比它更安全且可执行的做法。
